## 背景

- 分支 B / C：uniform-8K 每個關鍵點的 restart 從 5 增為 7，並把每個 run 的滑移數記為共變量。

判定規則、描述性分析與對應表都在 2026-10-16、任何 C0 數據之前寫進 028。

## 結果（028 事先寫定的描述性分析）

輸出：`results/capacity/explore-c0-20261016/analysis.json`，由 `benchmarks/c0_analysis.py` 產生；raw/ 不進 git。

| boot | 滑移段 n_b | 出現的模式 | P50 的中位數（ms） |
|---|---|---|---|
| b1 | 0 | low | 2,473.6 |
| b2 | 2 | high、low | 2,474.1 |
| b3 | 1 | high、low | 2,474.4 |
| b4 | 1 | high、low | 2,475.0 |
| b5 | 0 | low | 2,475.1 |
| b6 | 1 | high、low | 2,475.1 |

- **滑移段總數**：5 段，平均每個有效 bench 0.21 段。
- **分散度**：D = 3.40（df 5），門檻 χ²₀.₉₅ = 11.07，未超過。
- **空 boot 規則不適用**：session 平均每個 bench 只有 0.21 段，低於規則要求的 1 段。
- **判定：Rrun → 分支 A。**
- **每個偏高 bench 的特徵**：
  - 剛好 1 段，長度 7（同一組的第 1–7 個位置）。
  - Y − m_A 為 337–338 ms；偏低的 bench 為 3–12 ms。
  - 24 個 bench 的 k_prom 全部等於滑移數。
  - 這和步驟 0 的 S3 一致：整組多等一個約 349 ms 的 2048-token prefill step。

**只報告、不作判定**（028）
- **同時出現兩種模式的 boot**：6 次中有 4 次。
- **起始組**：
  - 每次 boot 的第 1 個 bench 都沒有滑移。
  - 第 2–4 個 bench 的起始組為 k = 11、11、11、11、16，其中 4 段都從 idx 89 開始。
  - 依 028 的寫法，起始組相同「暗示由 client 或時間鎖定的觸發」，而不是 server 狀態。這裡只記錄，不判定成因。
- **k ∈ {8, 16, 24} 的集中**：5 段中只有 1 段（0.2），隨機機率是 0.125，binomial 上尾 p = 0.49。
  - 沒有重現，和步驟 0 的 S1 一致。
- **偏高比例**：5 / 24 = 21%，Phase 1 為 8 / 12 = 67%。
  - 可能的原因包括 nvidia-smi 的 1 Hz 取樣（028 事先列出的限制），以及 session 之間本來就有的差異（例如桌面上開著的程式不同）。
  - 這次的資料無法區分這些原因，也沒有事先寫定的檢定。
- **Fhw**：沒有任何 bench 被標記，5 段滑移都在乾淨的 bench。
  - 判定依據是 bench 的 SM 時脈中位數與 boot 中位數的比值，門檻 0.95。
  - 每個 bench 的取樣窗內，最低的 SM 時脈為 172–180 MHz。這只是照實記錄，不在判定規則內。
- **Foff**：各 boot 的 P50 中位數相差 0.06%，低於 1%，不標記。

**檢定力**（028 已事先說明）
- 全部只有 5 段，D 大約只能偵測 5 倍以上的 boot 間差異。
- 所以 Rrun 的意思是「沒有偵測到 boot 層級的差異」，不代表已經證明現象只發生在 run 層級。
- 步驟 0 曾看到 Core r2 的滑移較多，暗示可能有 boot 層級的成分。這次沒有重現，但較小的差異仍然無法偵測。

## 決策

1. **`configs/capacity.toml` 的 `c0_branch = "A"`**：預設協定。
   - 每個 workload 的 n_near 都是 5，不記錄滑移共變量。
   - 依 028，分支不改變 SLO、時間窗、統計量、guard band、上限、搜尋與確認規則、workload 或 hypothesis。
   - 不依模式排除任何 run，因為排除會讓容量偏高。
2. **不判為分支 D**：
   - D 的條件是發現 harness 或 client 的缺陷。
   - 24 個 bench 全部有效，k_prom 全部吻合，FS-order smoke 也通過。
   - 起始組集中在 idx 89 是一個成因未明的現象，028 把它列為只報告，不是缺陷。
3. **8K 滑移的觸發時點列入 Future Work，不再追查**：
   - 使用者 2026-10-15 的指示是「先有限度排查」，而 028 的 C0 只決定分支；任何追加探針都需要新的 decision log。
   - 列入的內容：起始組集中、第 1 個 bench 沒有滑移、偏高比例與 Phase 1 不同。
4. **填入凍結證據**：`[freeze]` 的 `fs_order_smoke`、`mini_smoke` 與 `c0_decision = "032"`。之後依 030 的順序凍結 §8。

## 為什麼

- 對應表在任何 C0 數據之前就寫定。看過結果之後再改 n_near 或分支，屬於事後修改。
- 只因為想保守就改用分支 B（n_near 7），也一樣是看過數據後改規則。
  而且 030 已經用 guard band m = 5% 與 n_near = 5 處理機率 q ≥ 0.45 的罕見模式；更罕見的模式在 8.9 已列為限制。

## 放棄的替代方案

- **依起始組集中改判 D**：沒有找到缺陷，只有成因未明的規律。不採用。
- **追加探針找出觸發點**（換 seed、改到達時間的偏移等）：超出 C0 的範圍，也會擴張研究問題。列為 Future Work。
- **為了保守改用分支 B 或 C**：屬於事後偏離事先登記的規則。不採用。
