## 限制

1. **只做描述**（041 §1.1）：沒有檢定，也沒有信賴區間。「holds」是事先定義的計數規則，不是統計結論。
2. **大部分數據與兩個門檻在設計前已經看過**（041 §5 第 2–4、12、13 項）。
   - F > 35 ms 是看過數據後才定的（已見的空隙 29.1–39.2 ms）。
   - 錨點 s + 5 ms 是看過 B0、G、K3 的 steps 之後才改的。
   - 所以 B0、G、K3 上的重現不是獨立的驗證。T、TG 的錨定計數是凍結之後才第一次看到。
3. **樣本小**：21 段（Advanced 8、C0 5、Core 8）。只有一台機器（RTX 5070 Ti，WSL2）、一個模型、一組 prompt（8,064 token），只有 8K uniform、C 8。
4. **C0 與 Core 只評估得到 L3、L4**：flag 關的數據沒有 F、Q 與 step，所以第 1、2、5 環在這兩個數據集沒有量到，非滑移組 L1 的條件也是空的（null）。
5. **L2 的逐組值不在 e1.json**：e1.json 只記錄滑移段的 n_dec 與每個 run 的中位數，沒有每個正常組的值；只用 e1.json 時，041 §1.2 的「正常組都是 3 個」只核對得到中位數 3。
   - 用同一批已核對 sha256 的輸入（本機的 steps 與 derived 的 arrival），照 `stage_e1.n_dec` 的定義重算（見「獨立檢查」）：201 個非滑移組（g 1–23）全部是 3，計入的 6 段全部是 4，加上 k 24 的 2 段為 8 / 8。這重現了 §1.2 的「正常組都是 3 個」。
6. **時鐘**：step 的時間戳是 runner 讀到 log 的 wall clock，取整到 ms，不是 step 結束的時刻。server 與 client 的時鐘不互相相減（041 §1.3、1.4）。
7. **raw/ 不進 git**：從 raw 到 e1.json 這一步，只能靠 WSL 上的原始檔與 raw_manifest 的 sha256 稽核。
8. **跨 session**：三個數據集來自三個 session，數字只用來描述，不合併（041 §0、§1.5）。
9. **只列出、不解讀的值**：Core 的 L3 範圍較寬；TG-r1 g 17 的 F 為 69.22 ms。
10. **取回時的 GPU 狀態**：兩次取回之前 `gpu_status.sh` 都印出 FREE，但 repo 中沒有保存輸出，只有操作者的紀錄（見「執行」第 2 項）。

## 能支持與不能支持

- **能支持**：
  1. 在三個已有的數據集上，每一段計入的滑移（Advanced 6、C0 5、Core 7）都觀察到該數據集量得到的每一環（Advanced 為 L1–L5，C0 與 Core 為 L3、L4）。
     - 不計入的段：k 24 的 2 段五環都成立；Core r1 的 k 9（連續段）依規則不評估 L3（`CO.runs[0].episodes[1].links.L3` 為 null），L4 成立。
     - 用的量與門檻都在取回 raw 之前定義並凍結；其中 F > 35 ms（L1）與錨定窗的終點 s + 5 ms 是看過數據之後才定的（041 §5 第 3、13 項，見限制 2）。每個輸入的 sha256 都有紀錄，可以稽核。
  2. 在 Advanced 的 B0、G、K3 中，position 0 的 F 尖峰和滑移一一對應（g 1–24 為 8 / 8 對 0 / 208），尖峰組多 1 個 decode-only step。
  3. 三個數據集都沒有 client 晚送出（041 的 client 類，> 100 ms）：段內送出延遲的最大值 Advanced 0.341、C0 0.298、Core 0.267 ms。
- **不能支持**：
  1. 鏈的因果。各環同時出現，不代表前一環造成後一環。
  2. 觸發和內容綁定還是和位置綁定（E1-P 的問題）。
  3. F 多約 15 ms 的根本原因（需要 profiling，041 §1.8）。
  4. 032 的「偏高比例和 Phase 1 不同」（需要多個 session，041 §1.8、A1）。
  5. T、TG 的尖峰會不會造成滑移（它們不做滑移分類）。
  6. 推廣到其他 seed、模型、長度、C 或 session。
  7. 改變任何判定（041 §1.1）。

## 對 E1-P 的意義（只寫 041 有寫的部分）

1. **E1-P 另外事先登記**（041 §1.6–1.7，DRAFT），讀法表、門檻與 A_prior 都已經固定。E1-D 的結果不改 E1-P 的設計、門檻或讀法：E1 不改任何判定（§1.1），E1-D 的規則也只能以新的 decision log 修訂（§1.7）。
2. **E1-P 用的是同一套程式**（§1.7 與程式）：
   - runner 用 E1-D 凍結的 `stage_e1.f_spikes`，N 200 時再用 `stage_e1.bench_episodes`（`run_stage_e1p.bench_e1`）；分析用 `stage_e1.chain_summary`（`stage_e1p_analysis.py`）；門檻讀 `configs/stage_e1.toml`。
   - 核對 `stage_e1.harness_sha256()` 仍等於 `freeze.e1_harness_sha256`（`87b937d1…`）的，§1.7 寫的是 plan 與分析；程式中三者都經 `stage_e1p_plan.e1_config()` 核對（runner 也呼叫它）。
   - e1.json 的 harness 就是這個值，所以 E1-P 的描述量和本文的量出自同一套程式。
3. **041 §1.6 的既有值在 e1.json 上重算，結果一致**：
   - A_prior = {32, 64, 88, 128, 176, 192}：在 15 個 run 的尖峰 idx（8 × `spike_groups`）中，出現至少 2 次的 idx 就是這 6 個。88 與 128 各 7 次、176 出現 4 次、32、64、192 各 2 次。

- **index 的對應**：

  - 頂層：`.harness_sha256`、`.stage_e1_sha256`、`.inputs_sha256`、`.descriptive_only`、`.decision`。
  - 總表：`X.summary.{episodes, continuous, outside_base_range, evaluable, with_a_failing_link, l1_rate_in_normal_groups, chain, start_idx}`，以及 `X.blocked`。
  - 每一段：`X.runs[i].episodes[j].{k, start_idx, position, length, continuous, in_base_range, links.L1–L5, values.*}`。

- **重算的數字**（只用 e1.json，算法如下）：
  - 201 / 0：Σ `A.runs[i].l1_in_normal_groups.groups` / `.spikes`。
  - 8 / 8 對 0 / 208：比對 `spike_groups` 與該 run 各段的 `k`；216 = 9 × 24（g 1–24）。

  - 各範圍與最大最小值：對相應欄位取 min / max；147 = 56 + 35 + 56 個 `send_lag_ms` 值。
  - 滑移率：(`episodes` + `continuous` + `outside_base_range`) ÷ run 數。
  - 99 / 60 個輸入：`inputs_sha256` 的鍵依路徑分類。
  - 尖峰與計數 3 的對應：比對 `n_counts_g1_23["3"]` 與 g 1–23 中的尖峰數。
  - 每個 run 的最小 margin：該 run 各尖峰 `margin_ms` 的最小值。
  - A_prior：15 個 run 的 8 × `spike_groups` 計次。
- **從輸入重算、不在 e1.json 的數字**（用 `inputs_sha256` 中同一批已核對的檔，見「獨立檢查」）：
  - Advanced 的 bench 層級送出延遲（0.052–0.457 ms，G-r1）：`stage_e1.send_lags_by_idx` 套在 bench.json 的 `start_times` 與 `latencies`。
  - Core 各 bench 的送出延遲範圍（r1 0.054–0.308、r2 0.099–0.348、r3 0.110–0.409 ms）：同一個函式套在 Core 的 bench json。
  - 每個 bench 192 個送出延遲：三個數據集的每個 bench 都是 N 200，`send_lags_by_idx` 的長度為 192。
  - 非滑移組的 n_dec（201 組都是 3）：`stage_e1.n_dec` 套在本機的 steps 與 derived 的 `arrival`。
